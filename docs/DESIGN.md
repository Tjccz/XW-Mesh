## 一、产品定位

### 1.1 一句话定义

**湘网组网是一套可完全自建、数据不出自己服务器的异地组网管理平台**——把分散在不同地点的电脑、服务器、NAS、软路由连成一张私有内网，让异地设备像在同一个局域网里一样互相访问。

它不是 VPN 客户端，也不是路由器固件，而是**组网的管理中枢**：把「给几十台设备配网、发密钥、开权限、看状态、查流量」这件事，从"逐台登机器敲命令"变成"在网页上点几下"。

### 1.2 目标用户

| 用户画像 | 规模特征 | 核心痛点 | 我们的解法 |
| --- | --- | --- | --- |
| **中小企业的 IT 负责人** | 10–200 台设备，2–10 个地点 | 用公网 IP + 端口映射管内网，安全差、配置散、人一走就没人看得懂 | 网页集中编排，配置留档可回滚，权限分角色 |
| **有多个场地的经营者**（门店、仓库、工厂、农场） | 3–30 个点，无专职 IT | 想远程看监控/收银/门禁，但不会配路由器，也不放心数据过第三方云 | 一条命令接入，子网代理打通整个内网段 |
| **技术团队 / 集成商** | 需要给客户交付组网方案 | 现有工具要么功能太少（只有连接），要么太封闭（不能自建、不能审计） | 控制面自研可定制，控制台可私有化部署 |
| **高校 / 科研单位的实验室** | 设备多、预算低、数据敏感 | 商业方案按设备收费，且数据要过厂商云 | 自建部署零订阅成本，数据全在自己机器 |

### 1.3 典型场景

**场景 A｜连锁门店统一管理**
长沙 5 家门店 + 1 个总仓。每家店一台收银主机和一台 NAS。
- 总部运维在控制台建一张网络，给 5 家店各生成一个接入密钥；
- 店长用密钥在一台小主机上执行一条命令，主机自动接入并把门店内网段 `192.168.x.0/24` 代理进虚拟网；
- 总部运维在家就能直接 `\\192.168.11.20\收银数据` 拉报表，不需要门店有公网 IP；
- ACL 规则限制：只有总部的 IP 段能访问门店的 445 端口，其他节点互相不可见。

**场景 B｜异地办公与研发环境**
研发在长沙、测试服务器在深圳机房、客户演示环境在北京。
- 三地各放一个节点，形成 P2P 直连；
- 开发用 `10.144.144.0/24` 内网地址直接连测试库，不用改 hosts、不用申请跳板机；
- 流量视图能看到哪条链路在跑数据，源端口异常时能及时定位。

**场景 C｜无人值守现场的远程维护**
农场、基站、充电桩等现场只有一台工控机。
- 接入密钥设置「有效期 30 天 + 最多 5 台设备」，到期自动失效，避免运维离职后留下后门；
- 工控机背后的 PLC、摄像头通过子网代理一并可达；
- 设备离线超过 10 分钟自动发企业微信告警——不用等客户打电话来问。

**场景 D｜高校实验室多组设备隔离**
一个实验室 3 个课题组共用一套网络。
- 用访问控制把 A 组的 `10.144.144.10-20` 与 B 组的 `10.144.144.30-40` 互相拒绝，但都允许访问公共的 `10.144.144.100`（共享存储）；
- 所有变更写审计日志，学校信息中心审计时可导出。

### 1.5 差异化价值（三条护城河）

1. **完全自主可控**——控制面与数据面都跑在客户自己的服务器上，不依赖任何厂商云。对数据敏感型客户（学校、医院、政府配套、制造业）这是**准入门槛级**的诉求，而不是加分项。
2. **配置可追溯**——每次参数变更都留快照，出问题能回答"上次生效的配置是什么""谁在什么时候改的""回到哪一版"。商业组网工具普遍不做这件事，而它恰恰是运维最痛的地方。
3. **场景化能力优先**——子网路由可视化编排、访问控制编译预览、统一用量与审计、异常主动告警。这些是"能不能用起来"的关键，而通用工具只解决"能不能连上"。

### 3.1 分层架构

```
┌───────────────────────────────────────────────────────────────────────┐

│  浏览器（Vue 3 SPA）     第三方系统（规划中的 OpenAPI）                 │
└──────────────────────────────┬────────────────────────────────────────┘
                               │ HTTPS（宝塔 Nginx 反代 + 证书）
┌──────────────────────────────▼────────────────────────────────────────┐
│  应用层 · 控制台服务（自研，可闭源）                                     │
│  ┌─────────────┬─────────────┬─────────────┬─────────────┐            │

└──────────────────────────────┬────────────────────────────────────────┘
                               │

│  节点层（客户设备）                                                     │
│  ┌──────────────────────┐    ┌──────────────────────┐                 │
│  │ 节点代理（Shell）      │───▶│ easytier-core        │                 │
```

### 3.2 控制面 / 数据面职责边界

| 维度 | 控制面（自研） | 数据面（复用 EasyTier 核心） |
| --- | --- | --- |
| 职责 | 网络编排、设备纳管、密钥签发、策略编译、配置下发、状态采集、审计告警 | 加密握手、NAT 穿透、P2P 打洞、路由转发、子网代理执行、ACL 执行 |
| 是否承载业务流量 | ❌ 完全不承载 | ✅ 全部业务流量 |
| 部署位置 | 一台服务器（可内网） | 每台设备 |
| 控制台宕机影响 | 无法改配置/看状态，**已建立的连接不受影响** | 无影响 |
| 更换/升级 | 随时可换 | 需逐台升级 |

> **这条边界的价值**：控制台只是"管理员"，不是"交换机"。它挂了业务照跑，这让自建部署的风险大幅降低——客户最担心的"管理平台一停整个网络就断"在这里不成立。

### 3.3 技术选型与理由

| 层 | 选型 | 理由 | 被否决的方案 |
| --- | --- | --- | --- |
| 前端 | Vue 3 + Vite 6 + Element Plus 2.9 | 国内资料多、表单密集型后台开发效率高、组件覆盖完整 | React（团队熟悉度低）、低代码（可定制性不足） |
| 图表 | 自绘 SVG | 零依赖、体积小、样式完全可控；本项目图表类型固定（柱状/曲线） | ECharts（+900KB，功能过剩） |
| 后端 | Node.js 22 + Express 4（ESM） | 与前端同语言降低协作成本；异步 IO 适合心跳密集场景；启动快便于容器化 | NestJS（样板代码多，收益不明显）、Go（需另配人力） |
| 数据库 | SQLite（`node:sqlite`） | 零外部依赖、单文件备份、WAL 支持并发读；本项目写少读多、单机规模 | PostgreSQL（过早引入运维负担）、MySQL（同上） |
| 鉴权 | 自签 JWT（HMAC-SHA256） | 无外部依赖，密钥落盘可持久化 | 引入 `jsonwebtoken` 库（可省） |
| 数据面 | EasyTier 官方二进制 | 上游在 NAT 穿透上投入最大，自研无意义；LGPL-3.0 下进程隔离调用不构成衍生作品 | 自研协议（成本高、质量难保证） |
| 节点托管 | systemd / 容器 | 覆盖 95% 的 Linux 场景；不引入 systemd 之外的依赖 | 自研守护进程（重复造轮子） |
| 部署 | Docker Compose | 单机即可起步；宝塔面板可视化管理 | K8s（规模不匹配） |

## 四、功能模块设计

### 4.1 网络管理

**职责**：定义一张虚拟网络的边界——网络名、网络密钥、虚拟网段、初始接入点、资源地域、中继模式。

**关键设计**

| 设计点 | 说明 |
| --- | --- |
| 网络密钥 | 32 字符随机串，是节点互相识别与加密的凭据。**只有同密钥同网络名的节点才能互通**，这是数据面的第一道隔离 |
| 虚拟网段 | 默认 `10.144.144.0/24`（避开 `10.0.0.0/8` 常见内网段与 `192.168.x.0/24` 家用段） |
| 初始接入点 | 新节点第一次上线时需要至少一个已知节点地址来完成握手。控制台提供公共接入点作为"引路人"，节点接入后自动发现其他成员 |
| 中继模式 | `auto` 优先 P2P 直连，打洞失败自动回退中继；`relay` 强制走中继（隐私优先）；`p2p` 禁用中继（成本优先，打不通就断） |
| 改名/改密钥的连带影响 | 网络密钥变更 → 该网络下**所有设备**的配置版本递增 → 全部重新下发。这是少数会触发全网变更的操作，界面需二次确认 |

### 4.2 设备纳管

**职责**：把一台陌生机器变成网络中的一个节点，并长期跟踪它的状态。

**接入链路时序（自助注册模式）**

```
管理员                控制台                      目标设备
  │                     │                            │
  ├─新建接入密钥 ───────▶│                            │
  │   (有效期/上限)       │                            │
  │                     │                            │
  ├─把命令发给现场 ──────────────────────────────────▶│
  │  curl ... | sh      │                            │
  │                     │◀──① GET /install.sh?key=ek_ │
  │                     ├──▶ 返回脚本（含控制台地址）  │
  │                     │                            │
  │                     │◀──② GET /api/agent/register │
  │                     │     校验密钥状态/有效期/上限 │
  │                     │     分配虚拟 IP              │
  │                     │     建 node 记录             │
  │                     ├──▶ NODE_TOKEN=... 虚拟IP=...│
  │                     │                            │
  │                     │◀──③ GET /api/agent/config   │
  │                     ├──▶ 完整 config.toml        │
  │                     │                            │
  │                     │      ④ 配置预检（本地试跑 8 秒）
  │                     │      ⑤ 注册 systemd 服务并启动
  │                     │                            │
  │                     │◀──⑥ POST /heartbeat（每 30 秒）
  │                     ├──▶ 更新状态/流量，返回配置版本
  │  ◀─控制台看到"在线"──┤                            │
```

**关键设计**

| 设计点 | 说明 |
| --- | --- |
| 双模式接入 | **预置令牌**（管理员先建设备，令牌写在脚本里）适合少量受控设备；**接入密钥**（设备自助注册）适合批量部署与现场无人操作 |
| 节点身份 | `instance_id` 由 `sha256("xw-mesh:" + token)` 推导为稳定 UUID。**不新增数据库字段**，且设备重装、服务重启后身份不变 |
| 虚拟 IP 分配 | 从网段 `.2` 起找第一个未占用地址；分配前校验冲突，避免两台设备抢同一 IP |
| 设备状态机 | `pending`（已发令牌未接入）→ `online`（120 秒内有心跳）→ `offline`（超时）→ `blocked`（管理员停止或密钥吊销）。`blocked` 优先级最高 |
| 配置版本 | 每次影响该设备的变更都让 `config_version` 递增，设备侧靠比对版本决定是否重新拉配置 |

### 4.3 密钥体系

**设计目标**：让"放行一台设备"这件事从"管理员操作"变成"设备自助"，同时保留收回能力。

| 能力 | 设计 |
| --- | --- |
| 有效期 | `expires_at` 为空表示永久；到期后注册与心跳均被拒绝 |
| 设备上限 | `max_nodes` 为 0 表示不限；达到上限后注册返回明确原因 |
| 使用量 | `used_count`（当前接入数）与 `register_count`（历史注册次数）分开统计——前者随设备删除下降，后者只增 |
| 吊销 | 状态置 `revoked` 后，**下一次心跳即通知设备停止服务**并 `systemctl disable`，无需人工登机器 |
| 恢复 | 支持恢复吊销，恢复后设备需重新心跳才回到在线 |

**为什么不做密钥分组/密钥继承**：复杂度上升但收益有限，本项目场景下"一网络多密钥 + 备注"已足够，靠命名规范即可管理。

### 4.4 子网路由

**问题**：节点接入后只能访问虚拟网内的设备，但用户真正想要的是**访问设备背后的整个内网**（如门店里的收银机、摄像头）。

**方案**：指定某台设备作为"子网代理"，把 `192.168.88.0/24` 整段路由进虚拟网。任何节点访问 `192.168.88.x` 时，流量经该代理设备转发到真实内网。

**设计要点**

| 要点 | 说明 |
| --- | --- |
| 一对多 | 一台设备可承担多个网段 |
| 网段校验 | 格式校验 + 同网络内重复检测（防止两条冲突路由导致流量黑洞） |
| 代理设备选择 | 界面只允许选择同网络内的设备，避免跨网络误配 |
| 与 ACL 的关系 | 子网代理的流量走 `forward` 链路，受转发类 ACL 规则约束。**"谁能访问我代理的网段"由 ACL 决定**，两模块配合使用 |

### 4.5 访问控制

**目标**：在一个"全互通"的虚拟网里，实现按需隔离。

**三层链路模型**（与上游语义对齐）

| 链路类型 | 作用方向 | 典型用途 |
| --- | --- | --- |
| `inbound` 入站 | 其他节点 → 本节点 | 限制谁能连我本机 |
| `outbound` 出站 | 本节点 → 其他节点 | 限制我能连谁 |
| `forward` 转发 | 经本节点转发的流量 | 限制谁能通过我访问子网代理的网段 |

**规则要素**：动作（允许/拒绝）· 协议（任意/TCP/UDP/ICMP/ICMPv6）· 源 IP 段 · 目标 IP 段 · 端口 · 优先级（数字越大越先匹配）· 是否记录状态 · 限速。

**关键设计：编译预览**

管理员填写的是"人话"，但下发给核心的是**枚举整数**。为了消除"我配的到底生效成什么样"的不确定性，界面提供**编译预览**弹窗，直接展示将要下发的 TOML 片段，支持复制与下载：

```toml
[[acl.acl_v1.chains]]
chain_type     = 3          # 转发
default_action = 2          # 默认拒绝

  [[acl.acl_v1.chains.rules]]
  action          = 1       # 允许
  protocol        = 1       # TCP
  priority        = 200
  source_ips      = ["10.144.144.0/24"]
  destination_ips = ["192.168.88.0/24"]
  ports           = ["445"]
  stateful        = true
```

**为什么不做 `group` 身份体系**：上游支持基于用户组下发策略，但需要把组密钥分发到全网设备，自建场景下运维成本高、收益低。本项目只做纯 IP 段策略，界面不暴露 group 概念，保持心智模型简单。

### 4.6 配置下发（核心安全设计）

**这是整个系统最关键的工程问题**：如何在不登机器、不断业务的前提下，把新配置安全地推送到远端设备。

**风险**：一台设备在几百公里外的门店，如果推送了一个语法错误或语义冲突的配置，设备重启失败 → 现场断网 → 只能派人去现场。

**三道防护**

| 闸门 | 机制 | 失败时的行为 |
| --- | --- | --- |
| **① 变更通知** | 变更落库后 `config_version` 递增；设备代理每 30 秒心跳时获知版本变化 | 心跳失败不影响当前运行 |
| **② 配置预检** | 设备拿到新配置后，先 `timeout 8 core -c new.toml` **试跑 8 秒**。退出码 124/143/130（超时被杀）视为配置合法；其他退出码视为配置错误 | 删除新配置，**当前配置继续运行，核心不重启**，预检日志留档 |
| **③ 原子替换** | 预检通过才执行：备份旧配置 → 替换 → 重启核心 | 重启失败可手工回滚（控制台还保留配置快照） |

**实测效果**：推送一个语法错误的 ACL 后，设备不掉线、不重启，控制台能看到失败原因。

**配置内容清单**（下发的完整 `config.toml`）

```toml
instance_name = "<设备名>"          # 显示用
hostname      = "<设备名>"
instance_id   = "<由令牌推导的 UUID>" # 稳定身份
```

### 4.7 状态与流量采集

**设计约束**：控制台**不能**主动连接设备。原因有两个——设备大多在 NAT 后没有公网入口；主动连接意味着要把 RPC 端口暴露到公网，显著扩大攻击面。

**因此统一采用「设备主动上报」模型。**

| 数据 | 采集方式 | 频率 |
| --- | --- | --- |
| 在线状态 | 心跳 | 30 秒 |
| 核心版本 / 平台 | 心跳携带 | 30 秒 |
| 邻居数 | 节点本地执行 `easytier-cli peer` 统计行数 | 30 秒 |
| 出口公网 IP | 心跳前本地探测默认路由源地址 | 30 秒 |
| 网卡收发字节 | 读 `/proc/net/dev` 中 `dev_name` 对应行 | 30 秒（入库节流 55 秒） |

**流量计算的难点与解法**

设备上报的是网卡**累计计数器**（单调递增），不是区间增量。存储侧直接入库，查询侧对相邻采样做**差分**得到区间流量。

| 问题 | 解法 |
| --- | --- |
| 心跳过密导致写放大 | 最小采样间隔 55 秒，未到间隔只更新节点状态、不写采样表 |
| 设备重启导致计数器归零 | 差分时判断 `当前值 >= 上次值`，否则按当前值作为增量（即视为"从 0 开始"） |
| 采样稀疏、有缺口 | 差分天然容忍缺口——只要有一条基线就能算，不需要连续采样 |
| 查询性能 | `traffic_samples(node_id, sampled_at DESC)` 联合索引；按小时/天分桶聚合 |

**状态判定**

| 状态 | 判定条件 |
| --- | --- |
| `online` | 120 秒内有心跳（心跳间隔 30 秒，即容错 4 次） |
| `offline` | 超过 120 秒无心跳 |
| `pending` | 从未上报过心跳 |
| `blocked` | 被管理员停止，或来源密钥被吊销（**优先于时间判定**） |

### 4.8 告警通知

**设计目标**：把"人去发现问题"变成"系统主动告诉人"。

**结构**

```
告警规则 (alert_rules)                通知渠道 (alert_channels)
  ├─ 事件类型：设备离线/密钥到期/配额超限      ├─ webhook（通用 JSON POST）
  ├─ 阈值：离线 10 分钟 / 到期前 7 天 / 配额 80%  ├─ 企业微信机器人
  ├─ 作用范围：全部网络 / 指定网络        ├─ 钉钉机器人（含加签）
  ├─ 通知渠道：可多选                     └─ 邮件（SMTP）
  └─ 静默期：同一目标 N 分钟内不重复告警
                    │
                    ▼
     对账扫描引擎（每 60 秒，scanWorkspace）
                    │
                    ▼
        告警事件 (alert_events) ──▶ 投递（失败自动重试）
                    │
                    ▼
              前端「告警中心」
```

**关键设计**

| 设计点 | 说明 |
| --- | --- |
| 对账而非埋钩子 | 每轮遍历启用规则算出「此刻应当告警」的目标集合 `expected`，与库中 `firing` 事件做差集。**不在业务写入路径埋通知钩子** —— 否则漏发/重发无法收敛，且新增事件类型就要改业务代码 |
| 状态机 | 事件只有 `firing` → `resolved` 两个状态；条件消失即自动置为 `resolved` 并发恢复通知，形成完整故障周期 |
| 天然去重 | 同一规则 + 同一目标已在 `firing` 时本就不在差集里，不会重复推送（无需额外去重逻辑） |
| 抖动抑制 | 规则可配静默期，静默期内的同目标异常不再重复打扰 |
| 投递重试 | 投递失败自动重试至多 2 次尝试（间隔 1.5 秒递增），仍失败则标记 `failed` 并记录尝试次数 —— 通知渠道本身故障必须能被发现 |
| 渠道健康回写 | 每次投递结果回写渠道的 `last_status` / `last_error`，界面有醒目提示，避免"渠道静默失效却没人知道" |
| 渠道自测 | 每条渠道提供"发送测试消息"按钮，避免上线后才发现 webhook 地址写错 |
| 出参脱敏 | SMTP 密码、加签密钥、Bearer 令牌一律以 `******` 出参；前端回传掩码时由 `stripMasked()` 还原为旧值，绝不让掩码落库 |
| 不上第三方依赖 | 企业微信/钉钉都是 HTTP POST JSON，直接用 `fetch` 实现；邮件用自研极简 SMTP 客户端（仅 `node:net` / `node:tls`），支持 465 隐式 TLS 与 587 STARTTLS，不引入需编译的依赖 |

**为什么重试必须有界**：扫描引擎是串行的，一台「黑洞地址」的 webhook（能建立连接但不返回）会把整轮扫描拖住。因此单次请求 15 秒超时、最多 2 次尝试，最坏约 31 秒；扫描器另有重入保护，上一轮未跑完则跳过本轮。

### 4.9 组织与权限

**四档角色模型**

```
ROLE_RANK = { viewer: 1, member: 2, admin: 3, owner: 4 }
```

| 角色 | 查看资源 | 重发配置/停止设备 | 增删改资源 | 成员管理 | 工作区设置 |
| --- | :-: | :-: | :-: | :-: | :-: |
| viewer 只读 | ✅ | ❌ | ❌ | ❌ | ❌ |
| member 成员 | ✅ | ✅ | ❌ | ❌ | ❌ |
| admin 管理员 | ✅ | ✅ | ✅ | ❌ | ❌ |
| owner 拥有者 | ✅ | ✅ | ✅ | ✅ | ✅ |

**设计要点**

- 权限判断统一走中间件 `requireMinRole('admin')`，不散落在各路由里手写条件——避免"漏判断"这类越权漏洞
- 所有资源查询强制带 `workspace_id` 过滤，跨工作区访问在 SQL 层就被隔离，不依赖应用层判断
- 老库升级时若某工作区没有 owner，自动把最早的管理员提升为 owner（否则工作区设置页无人可用）

### 4.10 审计日志

**设计原则**：**写操作必留痕，且留痕不可绕过。**

| 记录字段 | 说明 |
| --- | --- |
| 操作者 | 用户名（设备侧操作为 `agent`） |
| 动作 | 约 35 类中文映射（如 `node.block` → 「停止设备」） |
| 对象 | 类型 + ID，例如 `node:12` |
| 详情 | 关键参数摘要（不含密钥明文） |
| 来源 IP | 取真实客户端 IP（`trust proxy` 后从 `X-Forwarded-For` 解析） |
| 时间 | ISO 8601 |

**注意**：审计记录写入与业务写入在同一个事务/同一进程内完成，不做异步队列——宁可慢一点，也不能因为队列丢失而留下审计空洞。

```
workspaces ─┬─< users
```

### 5.2 表设计

| 表 | 关键字段 | 设计说明 |

| `workspaces` | `name` / `slug` / `plan` | 工作区即租户；`plan` 决定配额 |

| `acl_rules` | `action` / `protocol` / `chain_type` / `src_cidr` / `dst_cidr` / `ports` / `priority` / `enabled` | 人话存储，下发时编译 |
| `traffic_samples` | `node_id` / `rx_bytes` / `tx_bytes` / `peer_count` / `sampled_at` | 累计值，查询时差分 |
| `audit_logs` | `username` / `action` / `target_type` / `target_id` / `detail` / `ip` | 只增不改 |
| `alert_rules` | `event_type` / `threshold` / `scope` / `channel_ids` / `silence_minutes` / `enabled` | 新增 |
| `alert_channels` | `type` / `config_json` / `enabled` | 新增，`config_json` 存 webhook 地址等 |
| `alert_events` | `rule_id` / `target` / `level` / `message` / `status` / `deliveries` / `fired_at` / `resolved_at` | 新增，告警全生命周期 |

### 5.3 迁移策略

**不引入迁移框架**，用 `ensureColumn()` 做增量补列：

```js
function ensureColumn(table, column, definition) {
  const cols = db.prepare(`PRAGMA table_info(${table})`).all()
  if (!cols.some(c => c.name === column)) {
    db.exec(`ALTER TABLE ${table} ADD COLUMN ${column} ${definition}`)
  }
}
```

| 规则 | 原因 |
| --- | --- |
| 补列语句必须全部执行完，才能创建依赖该列的索引 | 老库补列前索引会报 `no such column`（实现中踩过） |
| 新列必须有默认值或允许 NULL | SQLite 的 `ALTER TABLE ADD COLUMN` 限制 |
| 不得为已存在表新增 UNIQUE 列 | SQLite 不支持，需用独立索引替代 |
| 所有迁移必须幂等 | 服务每次启动都会执行 |

## 六、接口设计

### 6.1 设计规范

| 项 | 约定 |
| --- | --- |
| 风格 | RESTful，资源名词复数，动作用子资源表示（`POST /nodes/:id/block`） |
| 前缀 | 全部挂在 `/api` 下；节点侧接口统一在 `/api/agent/*` |
| 鉴权 | 管理接口用 `Authorization: Bearer <jwt>`；节点侧用 URL 上的 `token` 或 `key` |
| 成功响应 | 直接返回资源对象或 `{ items, summary }` |
| 错误响应 | 统一 `{ error: "中文提示" }`，用恰当 HTTP 状态码（400/401/403/404/409/429） |
| 分页 | `limit` + `offset`，响应带 `total` |
| 时间 | ISO 8601 字符串（UTC），前端按本地时区渲染 |
| 导出 | `?format=csv` 或独立 `/export.csv` 端点，带 UTF-8 BOM 保证 Excel 中文不乱码 |

### 6.2 接口清单

**认证 `/api/auth`**

| 方法 | 路径 | 权限 | 说明 |
| --- | --- | --- | --- |

### 6.3 节点侧协议约定

节点与控制台之间是**纯 HTTP 文本协议**，刻意保持极简——因为节点侧要能在最简陋的环境（BusyBox、老内核）跑通。

| 接口 | 请求 | 响应 |
| --- | --- | --- |
| `/register` | `GET ?key=&hostname=&arch=&platform=` | `KEY=VALUE` 纯文本（`NODE_TOKEN=` / `NODE_NAME=` / `VIRTUAL_IP=` / `NETWORK_NAME=` / `RPC_PORT=` / `CONFIG_URL=`） |
| `/heartbeat` | JSON POST | JSON（`ok` / `revoked` / `configVersion` / `syncInterval`） |
| `/config` | `GET ?token=` | TOML 纯文本 |

**为什么注册接口返回 `KEY=VALUE` 纯文本而不是 JSON**：Shell 里解析 `KEY=VALUE` 用 `sed -n 's/^NODE_TOKEN=//p'` 一行搞定，解析 JSON 需要 `jq`（很多精简系统没有）。这是刻意的取舍——**降低节点侧依赖比接口优雅更重要**。

**吊销联动约定**：只要响应体里出现 `"revoked":true`，节点代理就必须停止并禁用自身服务。这个约定极简且无歧义，避免了复杂的错误码协商。

## 七、关键技术方案

### 7.1 与 EasyTier 的集成边界

| 项 | 决定 |
| --- | --- |
| 集成方式 | **进程间调用**：控制台生成 `config.toml` → 节点执行 `easytier-core -c config.toml` |
| 是否修改源码 | **否**。不分叉、不打补丁 |
| 依赖的接口面 | 仅「读 TOML 启动」这一个稳定接口 |
| 许可证 | EasyTier 为 **LGPL-3.0**。进程隔离调用 + 不修改源码 → 控制面为独立作品，可闭源 |
| 版本策略 | `ET_VERSION` 可配置；新旧核心可共存；升级前核对上游 LICENSE |
| 声明义务 | 分发时随附 `THIRD-PARTY-NOTICES.md`，保留上游许可证与版权声明 |

> **为什么不复用上游的 `-w` Web 协议**：那是私有协议，用它等于把控制面绑死在上游演进节奏上，且需要自己实现服务端。自研通道虽然多写代码，但换来了完全的解耦。

### 7.2 配置编译

把数据库里的"人话"编译成上游要求的枚举整数：

| 语义 | 存储值 | 下发值 |
| --- | --- | --- |
| 链路类型 | `inbound` / `outbound` / `forward` | `1` / `2` / `3` |
| 动作 | `allow` / `deny` | `1` / `2` |
| 协议 | `any` / `tcp` / `udp` / `icmp` / `icmpv6` | `5` / `1` / `2` / `3` / `4` |
| 优先级 | 1–65535 整数 | 同值，`ORDER BY priority DESC, id ASC` |

> **易错点**：上游的 `priority` 是**数字越大越先匹配**，与多数防火墙"序号越小越优先"的直觉相反。界面文案需要明确提示，避免管理员配反。

编译产物同时计算 sha1 前 12 位作为**指纹**写入配置快照，用于快速判断"两台设备的 ACL 是否一致"。

### 7.3 虚拟 IP 分配

```
输入：虚拟网段 CIDR（如 10.144.144.0/24）、该网络已用 IP 集合
输出：可用 IP

规则：
  .0       网络地址，保留
  .1       预留给网关/未来用途
  .2 起    按序分配
  .255     广播地址（/24 时），保留
```

分配前做冲突校验；用户手工指定 IP 时也走同一套校验，拒绝越界与占用。

### 7.4 多租户隔离

| 层 | 措施 |
| --- | --- |
| 数据层 | 所有业务表带 `workspace_id`，所有查询强制 `WHERE workspace_id = ?` |
| 应用层 | JWT 中携带 `ws` 声明，中间件解析后注入 `req.user.ws`；路由代码不得使用前端传入的 workspaceId |
| 权限层 | `requireMinRole(role)` 中间件统一拦截 |
| 测试保障 | 冒烟测试含**跨工作区越权访问**用例，确保返回 404/403 而非泄漏数据 |

### 7.5 通知投递

| 渠道 | 实现 | 报文形态 |
| --- | --- | --- |
| 通用 Webhook | `POST` JSON | `{ event, level, target, message, time, workspace }` |
| 企业微信机器人 | `POST` 到 webhook URL | `{ msgtype: "markdown", markdown: { content } }` |
| 钉钉机器人 | `POST` 到 webhook URL | `{ msgtype: "markdown", markdown: { title, text } }`（支持加签时附 `timestamp`+`sign`） |
| 邮件 | 直接实现 SMTP 客户端（`node:net` / `node:tls`），支持 AUTH LOGIN 与 STARTTLS | RFC 5322 文本邮件 |

**投递可靠性**：每条事件记录每个渠道的投递结果（`pending` / `sent` / `failed` + 错误摘要 + 重试次数）。失败重试 3 次（间隔 5s/15s/45s）。**通知渠道本身故障必须可见**——否则会出现"以为配了告警，其实一直在失败"的静默失效。

### 7.6 前端工程

| 项 | 方案 |
| --- | --- |
| 路由 | Vue Router，`/dashboard` `/networks` `/nodes` `/access-keys` `/subnets` `/acl` `/metrics` `/usage` `/alerts` `/audit` `/workspace` `/members` |
| 状态管理 | 不引入 Pinia/Vuex——页面各自请求，跨页共享的只有登录态与工作区信息，放在轻量模块即可 |

| 权限渲染 | `canManage` 计算属性控制按钮可见性（**仅 UI 层收敛，真正拦截在后端**） |
| 主题 | 青蓝主色 `#0d9488`，浅色主题；表格密集页用紧凑列宽与短时间格式 |
| 构建产物 | `web/dist` 由后端静态托管，生产环境只需跑一个进程 |

## 八、安全设计

### 8.1 威胁模型

| 威胁 | 影响 | 对策 |
| --- | --- | --- |
| 节点令牌泄漏 | 攻击者冒充设备接入网络 | 令牌随机 32 字符且唯一；生产环境强制 HTTPS 防止链路窃听；支持随时移除设备 |
| 接入密钥泄漏 | 攻击者批量接入设备 | 密钥可设有效期 + 设备上限；支持即时吊销；吊销后已接入设备自动下线 |
| 控制台被入侵 | 全部网络配置暴露 | 反代 + HTTPS；控制台端口仅内网监听；四档最小权限；全部写操作审计；登录密码 scrypt 加盐 |
| 网络密钥泄漏 | 攻击者可加入虚拟网 | 网络密钥与接入密钥分离；密钥可轮换（触发全网重新下发） |
| 恶意节点横向扫描 | 内网暴露 | 默认拒绝的 ACL + 按需放行；子网代理流量受转发规则约束 |
| 配置下发被中间人篡改 | 设备被下发恶意配置 | HTTPS 传输；配置预检阻止非法配置启动；配置快照可追溯 |
| 审计日志被篡改 | 无法追责 | 审计表只增不改；备份文件中包含审计数据 |
| 代理服务器被攻击（若启用中继） | 流量被嗅探 | 数据面端到端加密；中继节点无法解密内容 |

### 8.2 安全基线（部署检查清单）

- [ ] `ADMIN_PASSWORD` 为强密码，首次登录后立即更换
- [ ] 配置域名 + HTTPS 并开启强制跳转
- [ ] `.env` 权限 600 且不入版本库
- [ ] `CONSOLE_URL` 设置为 https 地址（否则节点令牌明文回连）
- [ ] 控制台端口不对公网开放（改为 `127.0.0.1` 绑定 + 反代）
- [ ] 接入密钥设置有效期与设备上限，不用的立即吊销
- [ ] ACL 默认动作设为「拒绝」，按需放行
- [ ] 每日备份已配置并**实际验证过恢复流程**
- [ ] 宝塔面板自身改端口 + 开启双因素
- [ ] 定期查看审计日志，关注异常登录与配置变更

## 十、性能与容量设计

### 10.1 关键指标

| 指标 | 目标值 | 达成方式 |
| --- | --- | --- |
| 控制台接口 P95 响应 | < 300 ms | SQLite 索引全覆盖；流量查询按时间窗裁剪 |
| 心跳接口吞吐 | ≥ 200 req/s | Express 单进程足够（1000 设备 × 30 秒 = 34 req/s） |
| 单工作区设备容量 | 1000 台 | 冒烟测试覆盖边界 |
| 配置下发延迟 | ≤ 30 秒 | 心跳轮询间隔决定 |
| 配置预检耗时 | < 8 秒 | 固定超时，不影响正常业务 |
| 数据库写入放大控制 | 流量采样 ≥ 55 秒间隔 | 节流写入 |

### 10.2 性能设计要点

| 场景 | 设计 |
| --- | --- |
| 心跳高频写入 | 单条 `UPDATE` + 条件写采样，避免事务与关联查询 |
| 流量趋势查询 | 先按 `sampled_at` 裁剪时间窗，再在内存中分桶，避免全表扫描 |
| 设备列表 | 一次性预取网络映射表，避免 N+1 查询 |
| 审计日志分页 | `LIMIT/OFFSET` + `(workspace_id, id DESC)` 联合索引 |
| 前端大表格 | 固定列宽 + 短时间格式，避免布局抖动；分页而非虚拟滚动（数据量可控） |

### 10.3 容量估算

| 规模 | 流量采样日增 | SQLite 月增长 | 建议 |
| --- | --- | --- | --- |
| 50 台设备 | 50 × 1440 ≈ 7.2 万条/天 | ≈ 10 MB | 无需处理 |
| 300 台设备 | ≈ 43 万条/天 | ≈ 60 MB | 建议 90 天滚动清理 |
| 1000 台设备 | ≈ 144 万条/天 | ≈ 200 MB | 建议按天聚合归档 |

> 未来优化：超过 90 天的采样按天聚合成 `traffic_daily` 汇总表，原始采样保留 30 天。
