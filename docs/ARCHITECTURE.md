# 架构设计

## 一、总体分层

```
┌─────────────────────────────────────────────┐
│  湘网组网控制台（自研 · 可闭源）              │
│  Web 前端 + 后端 API + 数据库                │
│  职责：设备纳管、网络编排、状态监控、审计      │
└───────────────┬─────────────────────────────┘
                │  ① 下发配置（自研通道）
                │  ② 采集状态（RPC 查询）
                ▼
┌─────────────────────────────────────────────┐
│  节点（客户设备 / 我们的服务器）              │
│  easytier-core（官方二进制，原样运行）        │
└───────────────┬─────────────────────────────┘
                │  ③ 数据面：P2P 直连打洞
                ▼
┌─────────────────────────────────────────────┐
│  其他节点                                     │
└─────────────────────────────────────────────┘
```

**核心原则：控制面全自研，数据面直接用上游。**

原因：数据面（NAT 穿透、加密、路由）是 EasyTier 投入最大的部分，自己重写既没意义也做不过；而控制面（管理、编排、场景适配）才是产品的差异所在，也是能形成壁垒的地方。

## 二、配置下发：两个方案与选型

EasyTier core 支持三种获取配置的方式：命令行参数、配置文件、Web 控制台（`-w`）。

| 方案 | 做法 | 优点 | 缺点 | 结论 |
|---|---|---|---|---|
| A. 复用 `easytier-web` 协议 | core 用 `-w` 连我们的控制台，由我们实现其配置下发服务端 | 与上游行为一致 | `-w` 是上游私有协议，需自己实现服务端并跟随上游演进；被上游协议绑死 | **不用** |
| B. 自研下发通道 | 控制台生成参数/配置 → 通过 SSH 或自研 agent 推送到节点 → 重启 core | 与上游完全解耦；参数可控可审计；上游升级不影响我们 | 需要处理节点连接与权限 | **采用** |

**选 B。** 具体形态：

- 首次接入：一条脚本完成"下载二进制 → 写入配置 → 注册系统服务 → 启动"
- 后续变更：由控制台推送新参数并重启服务；节点侧只需一个极薄的执行入口

这样，我们的控制台**不依赖任何 EasyTier 私有接口**，上游怎么变都不影响产品的控制面。

## 三、状态采集

不做自研探测，直接用 core 自带的 RPC 能力：

```
easytier-cli -p 127.0.0.1:15888 peer    # 节点列表与连接状态
easytier-cli -p 127.0.0.1:15888 route   # 路由表 / 子网代理
easytier-cli -p 127.0.0.1:15888 node    # 本节点信息
```

控制台侧通过节点上的轻量 agent（或按需 SSH）周期性拉取，落库后供前端展示。

> RPC 端口默认 15888，可自定义；注意不要对公网暴露，仅监听回环或内网。

## 四、为什么不分叉 EasyTier

三条理由，任何一条都足够：

1. **许可证**：LGPL-3.0 下，修改本体并分发就要开源修改部分，直接影响商业化自由度。
2. **维护成本**：上游迭代很快（2.4 → 2.6 仅数月），fork 之后每次都要人工合并。
3. **没有收益**：产品价值在管理层，不在协议层。花在 fork 维护上的时间，换不来任何差异化。

**唯一例外**：如果确实发现必须在 core 内实现的刚需能力，优先走上游提 PR；实在不行再考虑"独立进程层适配"，而不是改源码。

## 五、技术选型建议

| 层 | 建议 | 理由 |
|---|---|---|
| 控制台前端 | Vue 3 + Vite + Element Plus | 上手快、国内资料多、适合表单密集型后台 |
| 控制台后端 | Node.js (NestJS) 或 Python (FastAPI) | 团队易上手；生态成熟 |
| 数据库 | SQLite（起步）→ PostgreSQL（多租户） | 先把事跑通，别过早引入运维负担 |
| 节点侧 | 官方 easytier-core + Shell/Python 薄封装 | 不引入额外运行时依赖 |
| 部署 | Docker Compose | 一台 2C2G 的云主机就能起步 |

前端与后端**全部属于我们自己的代码**，与 EasyTier 无耦合，可自由闭源。

## 六、数据模型（初稿）

```
user        用户（后续多租户再加 workspace）
network     网络：名称、密钥、虚拟网段、创建者
node        节点：所属网络、主机名、平台/架构、公网 IP、最后在线时间、状态
node_config 节点当前生效的配置快照（便于回滚与审计）
audit_log   操作日志：谁在什么时候改了哪个网络的什么参数
```

`node_config` 是差异化关键之一：客户网络出问题时，"上次生效的配置是什么"能省掉大量排查时间，而这一点上游控制台并不强调。

## 七、风险与对策

| 风险 | 对策 |
|---|---|
| 上游改协议或行为，影响兼容 | 控制面与上游解耦（方案 B），仅依赖命令行参数这一稳定接口 |
| 上游许可证再次变更 | 锁定当前使用的 core 版本，升级前先核对 LICENSE；保留旧版本二进制 |
| 中继带宽成本失控 | MVP 阶段不提供中继；有需求再评估自建中转节点与计费 |
| 被指"套壳" | 明确声明使用 EasyTier 开源核心；把力气花在上游没有的场景化能力上 |
