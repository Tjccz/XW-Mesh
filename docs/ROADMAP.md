# 迭代计划

> 原则：**先跑通一条闭环，再谈功能。** 每个阶段结束必须有一个能被别人验证的结果。

---

## 一、已完成

### 阶段 1｜节点接入链路（地基）

| 目标 | 不写界面，先用脚本把「陌生机器 → 网络节点」这条链路打通 |
| --- | --- |
| 成果 | `server/src/templates/node-install.sh`（306 行） |
| 验收 | 在全新机器上执行一条命令，另一台机器能 ping 通它的虚拟 IP |

实现要点：

- **双模式脚本**：A 预置令牌（脚本内置 token）/ B 接入密钥自助注册（`?key=ek_xxx`，设备自己领身份）
- 架构识别覆盖 `x86_64` / `aarch64` / `armv7` / `armv7hf` / `armhf` / `mips` / `mipsel` / `arm` / `riscv64`
- 依赖安装兼容 `apt` / `yum` / `apk`
- 核心下载带 `ghfast.top` 镜像回退（国内可用）
- 自动注册 systemd 主服务 + 代理定时器（30 秒）

### 阶段 2｜控制台骨架

### 阶段 3｜设备纳管闭环

| 目标 | 从「看」升级到「管」 |
| --- | --- |
| 成果 | 配置下发通道 + 配置快照 + 审计日志 + 一键回滚 |

**关键升级**：下发通道从「命令行参数」升级为「**完整 TOML 文件**」，并加入**配置预检**（见下）。这是从「能用」到「敢用」的分水岭。

## 三、下一步候选

按「对真实使用价值」排序，不是按实现难度：

| 优先级 | 能力 | 价值 |
| :-: | --- | --- |
| 高 | **真实两地压力验证** | 用真实网络跑一周，收集打洞成功率、延迟、断线重连数据，反哺默认参数 |
| 中 | **设备分组与标签** | 设备多了以后按「场地/角色」分组，ACL 可面向分组配置 |
| 中 | **配置模板** | 网络级模板（小办公室 / 门店 / 远程办公），一键套用，减少重复配置 |
| 中 | **开放 API Token** | 让第三方系统（或脚本）能调控制台接口做自动化运维 |
| 中 | **批量操作** | 批量重启、批量重发配置、批量吊销密钥 |
| 低 | **SSO 登录** | LDAP / OIDC，面向企业内网部署场景 |
| 低 | **存储后端可选** | PostgreSQL 选项，面向高并发多租户场景 |
| 低 | **国际化** | 中英双语 |
| 低 | **移动端适配** | 手机上查看状态与紧急操作 |

## 四、明确不做

| 不做 | 原因 |
| --- | --- |
| 修改 EasyTier 源码 | 触发 LGPL-3.0 义务，且产品价值在管理层不在协议层 |
| 自研客户端 App / GUI | 上游已有成熟的 Windows/macOS/Android 客户端，重复造没有意义 |
| 自建中继节点运营 | 带宽成本是真金白银，需要先有付费场景再评估 |
| 在线支付与计费系统 | 套餐模型已就位用于演示，真实收款涉及资质与对账，不是当前重点 |
| 引入迁移框架 | `ensureColumn()` 已能覆盖全部增量升级，加框架只增加运维负担 |
| ACL 的 group 身份体系 | 需要把密钥分发到全网设备，自建场景成本高收益低；纯 IP 段策略已够用 |

## 五、里程碑判断标准

用一句话检验产品是否立住：

> **「我能不能在 10 分钟内，把一台从没碰过的新机器，接入到另一处场地的那张网里？」**

答案是「能，而且不用我在旁边指导」—— 产品就立住了。

当前状态：**脚本层面已达成**（一条 `curl | sudo sh` 即可），待真实异地环境实测确认。

下一个里程碑用另一句话检验：

> **「设备半夜掉线，我是不是第二天早上打开手机就能知道，而不是等同事打电话来问？」**

当前状态：**已达成**（告警中心 + 企业微信/钉钉/邮件/Webhook 四类通知，见 `server/src/services/alerts.js`、`notify.js`）。

再下一个里程碑：

> **「出了告警，我能不能一眼看出是哪条规则报的、通知发到了谁、有没有发失败？」**

当前状态：**已达成**（事件带规则名与逐渠道投递明细；渠道保留最近投递结果与失败原因，静默失效可见）。

接下来要回答的是更硬的问题：

> **「把它部署到真实两地，跑一周，打洞成功率是多少？掉线后多久能自愈？」**

这需要真实网络数据，无法靠写代码回答。
